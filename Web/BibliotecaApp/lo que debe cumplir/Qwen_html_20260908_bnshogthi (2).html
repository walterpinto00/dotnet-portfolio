🗑️ Delete de Autor

Arquitectura en Capas con Services + ViewModels - ¡Último paso del módulo Autor!

🧠 Explicación simple para tus aprendices

El Delete es como un "are you sure?" (¿estás seguro?). Tiene dos pasos:

👁️ DELETE GET

Muestra los datos del autor y pregunta: "¿Seguro que quieres eliminar esto?"

🗑️ DELETE POST

El usuario confirma → se elimina el registro de la base de datos.

Es como cuando vas a borrar un archivo importante: primero te muestra qué vas a borrar, y luego te pide confirmación.

🔄 Flujo del Delete

GET (cuando el usuario hace clic en "Eliminar")

1. Usuario hace clic en "Eliminar"
Navegador envía GET a /Autor/Delete/5
↓
2. Controlador Delete GET
Pide al servicio: "dame los datos del autor con id 5 para mostrarlos en la confirmación"
↓
3. Servicio
Busca el autor y lo mapea a un ViewModel de confirmación
↓
4. Vista Delete
Muestra los datos del autor y un botón "Eliminar" para confirmar

POST (cuando el usuario confirma la eliminación)

1. Usuario hace clic en "Eliminar" (confirmar)
Navegador envía POST con el Id del autor
↓
2. Controlador Delete POST
Recibe el Id y llama al servicio para eliminar
↓
3. Servicio
Busca el autor, lo elimina de la base de datos (y sus libros por Cascade)
↓
4. Redirección
Vuelve al Index sin el autor eliminado

🔨 Implementación Paso a Paso

1 Crear el ViewModel para Delete

ViewModels/AutorDeleteViewModel.cs

¿Dónde? Clic derecho sobre la carpeta ViewModels → Agregar → Clase → nombrar AutorDeleteViewModel.cs

namespace BibliotecaApp.ViewModels
{
    public class AutorDeleteViewModel
    {
        public int Id { get; set; }
        public string Nombre { get; set; } = string.Empty;
        public string Nacionalidad { get; set; } = string.Empty;
        public DateTime? FechaNacimiento { get; set; }
        public int TotalLibros { get; set; }
    }
}
💡 ¿Por qué un ViewModel específico para Delete?

Porque la vista de confirmación necesita mostrar datos específicos:

  • Id → Para saber cuál eliminar (se envía en el POST)
  • Nombre, Nacionalidad, FechaNacimiento → Para mostrar al usuario qué está a punto de borrar
  • TotalLibros → ¡Importante! Para avisar cuántos libros se eliminarán también (por el Cascade Delete)
⚠️ ¿Por qué es importante mostrar el TotalLibros?

Porque en el DbContext configuraste DeleteBehavior.Cascade entre Autor y Libro. Esto significa que si eliminas un autor, también se eliminan todos sus libros automáticamente. El usuario debe saber esto antes de confirmar.

Ejemplo: si el usuario ve "Gabriel García Márquez tiene 5 libros", sabe que al eliminar al autor, también perderá esos 5 libros.

using BibliotecaApp.ViewModels;

namespace BibliotecaApp.Services
{
    public interface IAutorService
    {
        Task<IEnumerable<AutorIndexViewModel>> ObtenerTodosAsync(string? buscar);
        Task<AutorDetalleViewModel?> ObtenerDetalleAsync(int id);
        Task<CrearEditarAutorViewModel?> ObtenerViewModelParaEditarAsync(int id);
        Task<bool> ActualizarAutorAsync(int id, CrearEditarAutorViewModel viewModel);
        Task<bool> CrearAutorAsync(CrearEditarAutorViewModel viewModel);
        
        // ✅ AGREGAR ESTAS DOS LÍNEAS:
        Task<AutorDeleteViewModel?> ObtenerParaEliminarAsync(int id);
        Task<bool> EliminarAutorAsync(int id);
    }
}
💡 ¿Por qué dos métodos?

Porque hacen cosas diferentes, igual que en el Edit:

  1. ObtenerParaEliminarAsync(int id): Solo lee. Busca el autor y devuelve un ViewModel con sus datos para mostrar en la confirmación. Lo usa el GET del Delete.
  2. EliminarAutorAsync(int id): Solo escribe. Recibe el Id y elimina el autor de la base de datos. Lo usa el POST del Delete.

3 Implementar los métodos en el Servicio

Services/AutorService.cs

¿Dónde? Abrir Services/AutorService.cs y agregar estos dos métodos al final (no borrar los que ya existen).

// ✅ AGREGAR ESTOS DOS MÉTODOS (dentro de la clase AutorService):

public async Task<AutorDeleteViewModel?> ObtenerParaEliminarAsync(int id)
{
    var autor = await _context.Autores
        .Include(a => a.Libros)
        .FirstOrDefaultAsync(a => a.Id == id);

    if (autor == null)
    {
        return null;
    }

    return new AutorDeleteViewModel
    {
        Id = autor.Id,
        Nombre = autor.Nombre,
        Nacionalidad = autor.Nacionalidad,
        FechaNacimiento = autor.FechaNacimiento,
        TotalLibros = autor.Libros.Count
    };
}

public async Task<bool> EliminarAutorAsync(int id)
{
    var autor = await _context.Autores.FindAsync(id);

    if (autor == null)
    {
        return false;
    }

    _context.Autores.Remove(autor);
    await _context.SaveChangesAsync();

    return true;
}
💡 ¿Qué hace cada método?

ObtenerParaEliminarAsync:

  1. Busca el autor por su Id incluyendo sus libros (necesitamos contarlos).
  2. Si no existe, devuelve null.
  3. Si existe, crea un AutorDeleteViewModel con los datos del autor y el total de libros.

EliminarAutorAsync:

  1. Busca el autor por su Id.
  2. Si no existe, devuelve false (el controlador lo convertirá en 404).
  3. Si existe, lo elimina con _context.Autores.Remove(autor).
  4. Guarda los cambios con SaveChangesAsync(). Aquí Entity Framework elimina automáticamente los libros asociados por el DeleteBehavior.Cascade.
  5. Devuelve true para indicar éxito.
⚠️ Importante sobre el Cascade Delete

Cuando llamas a _context.Autores.Remove(autor), Entity Framework NO necesita que elimines los libros manualmente. Como configuraste DeleteBehavior.Cascade en el DbContext, EF se encarga de eliminar todos los libros asociados automáticamente cuando llamas a SaveChangesAsync().

// GET: AUTORS/Delete/5
public async Task<IActionResult> Delete(int? id)
{
    if (id == null)
    {
        return NotFound();
    }

    var viewModel = await _autorService
        .ObtenerParaEliminarAsync(id.Value);

    if (viewModel == null)
    {
        return NotFound();
    }

    return View(viewModel);
}

Delete POST (ejecutar la eliminación):

❌ BORRAR ESTO (el Delete POST viejo)

[HttpPost, ActionName("Delete")]
[ValidateAntiForgeryToken]
public async Task<IActionResult> DeleteConfirmed(
    int? id)
{
    var autor = await _context.Autores
        .FindAsync(id);
    if (autor != null)
    {
        _context.Autores.Remove(autor);
    }

    await _context.SaveChangesAsync();
    return RedirectToAction(nameof(Index));
}

✅ REEMPLAZAR CON ESTO

// POST: AUTORS/Delete/5
[HttpPost, ActionName("Delete")]
[ValidateAntiForgeryToken]
public async Task<IActionResult> DeleteConfirmed(
    int id)
{
    var exito = await _autorService
        .EliminarAutorAsync(id);

    if (!exito)
    {
        return NotFound();
    }

    return RedirectToAction(nameof(Index));
}

Antes Ahora
@model BibliotecaApp.Models.Autor @model BibliotecaApp.ViewModels.AutorDeleteViewModel

⚠️ IMPORTANTE: El campo hidden del Id SÍ está aquí

A diferencia del Edit, en el Delete sí necesitamos un campo hidden con el Id:

<input type="hidden" asp-for="Id" />

¿Por qué? Porque el formulario se envía a /Autor/Delete (sin el Id en la URL). El Id debe venir del formulario. Pero como el AutorDeleteViewModel solo tiene datos de lectura (no hay nada peligroso), es seguro.

Además, el formulario tiene [ValidateAntiForgeryToken] que protege contra ataques CSRF.

💡 ¿Por qué la alerta de advertencia?

Es una buena práctica de UX (experiencia de usuario). El usuario debe saber que:

  • La acción es irreversible
  • Se eliminarán otros datos asociados (los libros)

Esto evita eliminaciones accidentales.

🎯 ¿Qué aprendieron tus aprendices?

  • El Delete tiene dos flujos: GET (mostrar confirmación) y POST (ejecutar eliminación). Cada uno llama a un método diferente del servicio.
  • El ViewModel de Delete es específico → Solo tiene los datos necesarios para la confirmación, incluyendo el TotalLibros para avisar al usuario.
  • El Cascade Delete es automático → Entity Framework elimina los libros asociados cuando eliminas el autor, gracias a DeleteBehavior.Cascade.
  • El campo hidden del Id SÍ va en el Delete → A diferencia del Edit, aquí el Id viene del formulario (no de la URL) porque el POST va a /Autor/Delete sin el Id.
  • La alerta de advertencia es buena UX → Avisar al usuario sobre consecuencias irreversibles evita errores.
  • El patrón se repite → Delete usa el mismo patrón que Edit: ViewModel → Interfaz → Servicio → Controlador → Vista.
  • Ya no necesitamos métodos auxiliares → AutorExists ya no es necesario porque el servicio se encarga de verificar.

🧹 Limpieza Final del Controlador

Ahora que todas las acciones (Index, Details, Create, Edit, Delete) usan el servicio, puedes hacer la limpieza final:

  1. Eliminar el método AutorExists → Ya no se usa.

  3. Eliminar los using innecesarios → BibliotecaApp.Data, BibliotecaApp.Models, Microsoft.EntityFrameworkCore.

El controlador quedará súper limpio: solo depende de IAutorService.
