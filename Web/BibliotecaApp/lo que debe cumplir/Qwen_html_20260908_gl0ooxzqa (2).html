✏️ Edit de Autor

Arquitectura en Capas con Services + ViewModels

🧠 Explicación simple para tus aprendices

El Edit es como el Create, pero con una diferencia: el formulario ya viene lleno con los datos actuales del autor.

📝 CREATE

Formulario vacío → el usuario llena → se guarda como nuevo

✏️ EDIT

Formulario con datos → el usuario modifica → se actualiza el existente

Por eso el formulario es idéntico en ambos casos. Vamos a crear UN solo ViewModel que sirva para los dos: CrearEditarAutorViewModel.

🔄 Flujo del Edit

GET (cuando el usuario hace clic en "Editar")

1. Usuario hace clic en "Editar"
Navegador envía GET a /Autor/Edit/5
↓
2. Controlador Edit GET
Pide al servicio: "dame los datos del autor con id 5"
↓
3. Servicio
Busca el autor, lo mapea al ViewModel y lo devuelve
↓
4. Vista Edit
Muestra el formulario con los datos ya llenos

POST (cuando el usuario hace clic en "Guardar")

1. Usuario hace clic en "Guardar"
Navegador envía POST con los datos del formulario
↓
2. Controlador Edit POST
Recibe el ViewModel, valida con ModelState.IsValid
↓
3. Servicio
Busca el autor en la BD, actualiza sus propiedades y guarda
↓
4. Redirección
Vuelve al Index con los datos actualizados

1 Crear el ViewModel para Create y Edit

ViewModels/CrearEditarAutorViewModel.cs

¿Dónde? Clic derecho sobre la carpeta ViewModels → Agregar → Clase → nombrar CrearEditarAutorViewModel.cs

using System.ComponentModel.DataAnnotations;

namespace BibliotecaApp.ViewModels
{
    public class CrearEditarAutorViewModel
    {
        [Required(ErrorMessage = "El nombre es obligatorio")]
        [StringLength(100, ErrorMessage = "El nombre no puede exceder 100 caracteres")]
        [Display(Name = "Nombre")]
        public string Nombre { get; set; } = string.Empty;

        [Required(ErrorMessage = "La nacionalidad es obligatoria")]
        [StringLength(50, ErrorMessage = "La nacionalidad no puede exceder 50 caracteres")]
        [Display(Name = "Nacionalidad")]
        public string Nacionalidad { get; set; } = string.Empty;

        [Required(ErrorMessage = "La fecha de nacimiento es obligatoria")]
        [DataType(DataType.Date)]
        [Display(Name = "Fecha de Nacimiento")]
        public DateTime? FechaNacimiento { get; set; }
    }
}
💡 ¿Por qué un ViewModel diferente para Create/Edit?
ViewModel ¿Para qué sirve? ¿Tiene Id?
AutorIndexViewModel Listar autores en una tabla ✅ Sí (para los links de acciones)
AutorDetalleViewModel Mostrar el detalle de un autor ✅ Sí
CrearEditarAutorViewModel Formulario de Create y Edit ❌ NO (el Id va por la URL)
🚨 ¿Por qué el Id NO está en este ViewModel?

Porque el Id no lo escribe el usuario. Viene de la URL: /Autor/Edit/5. El 5 es el Id. Si lo pusiéramos en el ViewModel como un campo oculto del formulario, un usuario malintencionado podría cambiarlo con las herramientas de desarrollador y editar otro autor. El Id siempre debe venir de la ruta, nunca del formulario.

💡 ¿Por qué las validaciones están aquí y no en el modelo?

Porque el modelo (Autor.cs) representa la base de datos. Las validaciones del formulario son reglas de la interfaz de usuario. Si mañana quieres que el nombre tenga máximo 50 caracteres en el formulario pero 200 en la base de datos, puedes cambiar el ViewModel sin tocar el modelo.

2 Agregar los métodos a la Interfaz del Servicio

Services/IAutorService.cs

¿Dónde? Abrir Services/IAutorService.cs y agregar DOS líneas (no borrar lo que ya existe).

using BibliotecaApp.ViewModels;

namespace BibliotecaApp.Services
{
    public interface IAutorService
    {
        Task<IEnumerable<AutorIndexViewModel>> ObtenerTodosAsync(string? buscar);
        Task<AutorDetalleViewModel?> ObtenerDetalleAsync(int id);
        
        // ✅ AGREGAR ESTAS DOS LÍNEAS:
        Task<CrearEditarAutorViewModel?> ObtenerViewModelParaEditarAsync(int id);
        Task<bool> ActualizarAutorAsync(int id, CrearEditarAutorViewModel viewModel);
    }
}
💡 ¿Por qué dos métodos y no uno?

Porque hacen cosas diferentes:

  1. ObtenerViewModelParaEditarAsync(int id): Solo lee. Busca el autor y devuelve un ViewModel con sus datos actuales. Lo usa el GET del Edit.
  2. ActualizarAutorAsync(int id, viewModel): Solo escribe. Recibe el Id y los datos nuevos, y actualiza la base de datos. Lo usa el POST del Edit.

Esto se llama Principio de Responsabilidad Única: cada método hace una sola cosa.

3 Implementar los métodos en el Servicio

Services/AutorService.cs

¿Dónde? Abrir Services/AutorService.cs y agregar estos dos métodos al final (no borrar los que ya existen).

// ✅ AGREGAR ESTOS DOS MÉTODOS (dentro de la clase AutorService):

public async Task<CrearEditarAutorViewModel?> ObtenerViewModelParaEditarAsync(int id)
{
    var autor = await _context.Autores.FindAsync(id);

    if (autor == null)
    {
        return null;
    }

    // Mapear del modelo al ViewModel
    return new CrearEditarAutorViewModel
    {
        Nombre = autor.Nombre,
        Nacionalidad = autor.Nacionalidad,
        FechaNacimiento = autor.FechaNacimiento
    };
}

public async Task<bool> ActualizarAutorAsync(int id, CrearEditarAutorViewModel viewModel)
{
    var autor = await _context.Autores.FindAsync(id);

    if (autor == null)
    {
        return false;
    }

    // Actualizar solo las propiedades permitidas
    autor.Nombre = viewModel.Nombre;
    autor.Nacionalidad = viewModel.Nacionalidad;
    autor.FechaNacimiento = viewModel.FechaNacimiento;

    await _context.SaveChangesAsync();

    return true;
}
💡 ¿Qué hace cada método?

ObtenerViewModelParaEditarAsync:

  1. Busca el autor por su Id con FindAsync (es más rápido que FirstOrDefaultAsync cuando buscas por clave primaria).
  2. Si no existe, devuelve null.
  3. Si existe, crea un nuevo ViewModel y copia los datos del autor al ViewModel.
  4. Devuelve el ViewModel para que el controlador se lo pase a la vista.

ActualizarAutorAsync:

  1. Busca el autor por su Id.
  2. Si no existe, devuelve false (el controlador lo convertirá en 404).
  3. Si existe, actualiza solo las propiedades permitidas (Nombre, Nacionalidad, FechaNacimiento). NO actualiza el Id ni ninguna otra propiedad.
  4. Guarda los cambios en la base de datos.
  5. Devuelve true para indicar que todo salió bien.
💡 ¿Por qué actualizamos propiedad por propiedad y no usamos _context.Update(autor)?

Porque el ViewModel no tiene Id. Si hiciéramos _context.Update(viewModel), EF Core no sabría qué registro actualizar. Además, actualizar propiedad por propiedad es más seguro: solo cambiamos lo que el usuario puede cambiar, nada más.

// GET: AUTORS/Edit/5
public async Task<IActionResult> Edit(int? id)
{
    if (id == null)
    {
        return NotFound();
    }

    var viewModel = await _autorService
        .ObtenerViewModelParaEditarAsync(id.Value);

    if (viewModel == null)
    {
        return NotFound();
    }

    return View(viewModel);
}

Edit POST (guardar los cambios):

❌ BORRAR ESTO (el Edit POST viejo)

[HttpPost]
[ValidateAntiForgeryToken]
public async Task<IActionResult> Edit(int? id, 
    [Bind("Id,Nombre,Nacionalidad,FechaNacimiento")] 
    Autor autor)
{
    if (id != autor.Id) return NotFound();

    if (ModelState.IsValid)
    {
        try
        {
            _context.Update(autor);
            await _context.SaveChangesAsync();
        }
        catch (DbUpdateConcurrencyException)
        {
            if (!AutorExists(autor.Id)) 
                return NotFound();
            else throw;
        }
        return RedirectToAction(nameof(Index));
    }
    return View(autor);
}

✅ REEMPLAZAR CON ESTO

// POST: AUTORS/Edit/5
[HttpPost]
[ValidateAntiForgeryToken]
public async Task<IActionResult> Edit(int id, 
    CrearEditarAutorViewModel viewModel)
{
    if (!ModelState.IsValid)
    {
        return View(viewModel);
    }

    var exito = await _autorService
        .ActualizarAutorAsync(id, viewModel);

    if (!exito)
    {
        return NotFound();
    }

    return RedirectToAction(nameof(Index));
}
💡 ¿Qué cambió en el Edit GET?
Antes Ahora
Usaba _context directamente Usa _autorService
Devolvía View(autor) (modelo de dominio) Devuelve View(viewModel) (ViewModel)
💡 ¿Qué cambió en el Edit POST?
Antes Ahora
Recibía un Autor con [Bind(...)] Recibe un CrearEditarAutorViewModel
El Id venía del autor.Id (del formulario) El Id viene de la URL (parámetro id)
Usaba _context.Update(autor) Llama a _autorService.ActualizarAutorAsync(id, viewModel)
Manejaba DbUpdateConcurrencyException Ya no necesita (el servicio lo maneja internamente)
Tenía el método AutorExists auxiliar Ya no lo necesita para Edit (lo hace el servicio)
💡 ¿Por qué el parámetro id ya no es int? sino int?

Porque en el POST, el Id siempre viene de la URL. Si la URL no tiene Id, ASP.NET ni siquiera va a entrar a este método (devolverá 404 automáticamente). Así que podemos recibirlo como int directamente, sin el ?.

💡 ¿Por qué ya no necesitamos [Bind(...)]?

¡Porque el ViewModel ya es seguro por diseño! Solo tiene 3 propiedades: Nombre, Nacionalidad, FechaNacimiento. No tiene Id, no tiene Libros, no tiene nada peligroso. Aunque un hacker intente enviar datos extra, el Model Binder los va a ignorar porque el ViewModel no los tiene.

🎯 ¿Qué aprendieron tus aprendices?

  • Un ViewModel puede servir para varias acciones → CrearEditarAutorViewModel sirve tanto para Create como para Edit porque el formulario es idéntico.
  • El Id NO va en el ViewModel de formularios → Viene de la URL. Es más seguro.
  • El Edit tiene dos flujos: GET (leer y mostrar) y POST (recibir y guardar). Cada uno llama a un método diferente del servicio.
  • Las validaciones van en el ViewModel → Con [Required], [StringLength], etc. El ModelState.IsValid del controlador las verifica automáticamente.
  • El servicio actualiza propiedad por propiedad → No usa _context.Update(). Es más seguro y explícito.
  • Ya no necesitamos [Bind(...)] → El ViewModel es seguro por diseño.
  • Ya no necesitamos el campo hidden del Id → El Id viene de la URL, no del formulario.
